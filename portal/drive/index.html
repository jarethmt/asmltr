    Portal drive — the generic remote-driver contract¶

    The wire contract for driving any computer through a Portal (DESIGN §6a in the asmltr-portal repo). Everything below is the interface each layer implements against — change it here first.

    The assistant ── asmltr core ── (device-gw relay) ── phone app ── BLE ── Portal dongle ── HID/CDC ── host

    The dongle is a composite USB HID keyboard+mouse + CDC serial. the assistant drives the host by (a) typing via HID and (b) reading the host's output back through the dongle's own CDC — no agent installed.

    1. BLE GATT (firmware implements; app uses)¶

    Existing service 00657665-5f61-736d-6c74-72706f72 + a last byte:

    byte name ops payload
    08 exec WRITE (chunked, load-style [flags][rsvd][seqBE] header) reassembled payload = [u8 mode][data…]; mode 0x01 = type data as HID keystrokes, 0x02 = write data to the host over CDC-TX
    09 ioback NOTIFY raw bytes the host wrote to the dongle's CDC (the return stream), MTU-chunked

    UUIDs: exec = …727408, ioback = …727409. The dongle also keeps the existing info/load/run/status/pair chars; exec/ioback are the generic-driver additions.

    exec mode 0x01 (HID) keystroke-script format¶

    data is a UTF-8 keystroke script, not raw ASCII — literal text types as-is, and {…} tokens are special keys / combos / delays, so recipes can open terminals:

    • Literals: powershell → types those chars.
    • Keys: {ENTER} {TAB} {ESC} {SPACE} {BKSP}
    • Combos: {GUI+r} (Win/Cmd+R) {CTRL+ALT+t} {GUI} {CTRL+c} — GUI=Windows/Command key.
    • Timing: {DELAY:500} (ms) — wait between steps (needed after opening a dialog).

    Example (open PowerShell on Windows): {GUI+r}{DELAY:400}powershell{ENTER}{DELAY:800}. The firmware parses this → HID reports. mode 0x02 (CDC) data is written to the host verbatim.

    2. Relay message shape (core ↔ app, over the device-gateway)¶

    • Server → app: { "type": "portal.exec", "mode": "hid"|"cdc", "data": "<base64>" } → app writes [mode][data] to the exec characteristic (chunking as needed).
    • App → server: { "type": "portal.io", "data": "<base64>" } — the drained ioback stream.
    • App → server (presence): { "type": "portal.present", "paired": bool, "name": "asmltr-portal-…", "host_os": "…" } answered on demand (also the vault-kill-switch presence check).

    The app auto-connects to a paired Portal in the background (battery-cheap, DESIGN §5) and relays both directions. A Portal console view shows the live ioback stream and can send a manual command.

    3. The session bridge + per-OS recipes (skill)¶

    Driving a host is: open a terminal (blind HID) → confirm via a CDC marker → start a serial-bridge REPL → stream commands over CDC. Each OS supplies a recipe { terminalOpen, probe, replBootstrap }:

    • terminalOpen — HID keystrokes to reach a shell. Windows: GUI+r, powershell, Enter. macOS: GUI+Space, Terminal, Enter. Linux: Ctrl+Alt+T (best-effort). Android: the ADB path (not HID-shell — see below).
    • probe — a one-liner that finds the dongle's serial port by VID/PID 303A:4002 (never a guessed COM) and writes a known marker to it. Marker returns via ioback ⇒ terminal confirmed + OS locked in (refines usb_host_os_set).
    • replBootstrap — a short line that bridges the dongle's serial ↔ the shell (reads commands from the port, writes stdout/stderr back). After it runs, commands flow as exec:cdc and results as ioback; no more blind typing. A screenshot is just a replBootstrap command that captures → downscales → JPEG → writes bytes to the port (few-second snapshot over BLE; text is instant).

    Android has no stock shell→serial redirect, so its recipe uses ADB (consented RSA key), not the CDC bridge; HID stays available for blind navigation. The recipe object marks transport: "adb".

    These recipes + the drive procedure live in a core asmltr skill (portal-drive) so every asmltr instance knows how to use a Portal to drive a device.

    4. Enrollment (persistent track)¶

    POST /v2/portal/enroll mints a short-lived, revocable token and returns the per-OS bootstrap one-liner that wraps asmltr mesh enroll (the already-shipped tooling). The enroll runs over the bridge (exec:hid to open a shell → run the one-liner), installs the mesh client (Windows newt as SYSTEM; the alias/SYSTEM gotchas are encoded in mesh/), registers the device + ssh/rd transports so it lands in the Fleet, then the victory lap: a session connects back over the mesh and paints SUCCESS on the target's own screen (GUI or console ASCII). The installer is just one script riding the bridge.

    5. Safety¶

    Driving is remote keyboard control of an arbitrary machine → the trust gate is non-negotiable: the Portal runs modules/commands only from its paired instance, one up-front consent per drive session, and the vault-kill-switch (unplug the Portal → the assistant can't use dongle-only credentials) is the physical counterweight. Never bypass OS elevation (UAC/sudo) — assisted, consented provisioning only.

    6. Install / uninstall (persistent track)¶

    The DRIVE track (§3) runs a host with no agent over the dongle. The persistent track (core/src/portal/enroll.js) is the other half: it JOINS a host onto asmltr's self-hosted mesh so asmltr can reach it by SSH/RDP afterwards — and tears that down cleanly. The installer is just one script riding the same bridge (§2): exec:hid to open a shell, then the one-liner below.

    Ownership: enroll.js owns only the logic. core/src/server.js (core owner, NOT this module) wires POST /v2/portal/enroll and the script-serving endpoint. The per-OS install/uninstall one-liners live in recipes.js (recipe.install(token, baseUrl) / recipe.uninstall(org)) so the shapes stay in one place.

    enroll({ os, deviceName, deviceId })¶

    asmltr-SIDE steps, in order: 1. find/create the device row (devices/store.js), platform = normalized OS — it lands in the Fleet immediately. 2. register ssh (:22) and rd (:3389) transports at their mesh aliases <slug>-ssh.mesh / <slug>-rd.mesh — the addresses asmltr reaches it on once the tunnel is up. 3. mint a short-lived, revocable one-time token (devices/enroll.js → enrollments, 15 min). The token is not a credential — it only authorizes the host to fetch its install script. 4. drive the already-shipped asmltr mesh enroll <device> --os <os> + asmltr mesh resource … (via execFile). Tolerant: if the mesh isn't provisioned the CLI says so and enroll returns mesh.status='not-configured' instead of failing — the device + token stay valid for a later bring-up.

    Returns { token, bootstrapCommand, device, mesh }.

    bootstrapCommand(os, token, baseUrl)¶

    The ONE line the host runs. Thin by design: it fetches the per-device mesh-client install script (authorized by token) from {baseUrl}/v2/portal/enroll/script?os=<os> and runs it. - Windows: elevated-PowerShell iwr … | iex. The fetched script registers newt as a SYSTEM scheduled task (mesh/deviceinstall.newtWindows). - Linux: curl -fsSL -H 'Authorization: Bearer <token>' … | sudo sh → a systemd newt unit. - macOS: same curl | sudo sh → a launchd olm daemon. - Android: no shell one-liner — enrollment is the ADB path; install() returns a note.

    teardown({ os, deviceName, deviceId })¶

    The reverse. Returns { uninstallCommand, ok, mesh, revoked, dropped_transports }: - uninstallCommand — the per-OS host one-liner that stops + removes the newt/olm unit/task and leaves the mesh (recipe.uninstall(org); unit/task names match mesh/deviceinstall.js exactly: newt-<org>-mesh, olm-<org>-mesh). - asmltr-side deregistration — revoke the device's credentials/token (vault delete + hash drop via devices/enroll.revoke), remove the mesh ssh/rd resources, and drop the ssh/rd transports.

    victoryLap(deviceId)¶

    After enroll, connect BACK over the mesh and paint SUCCESS on the target's own screen — the moment that proves the round trip end to end. It SSHes to the device's ssh transport alias using the asmltr host's mesh SSH identity (mesh/sshkey; its PUBLIC key is what Portal provisioning dropped into the target's authorized_keys), and runs a remote one-liner that prints a bold ASCII ENROLLED ✓ / asmltr banner to the SSH session and broadcasts it to any logged-in console (wall on Linux/macOS, msg * on Windows). A GUI variant (noted, not built) would instead push a desktop toast: notify-send / osascript -e 'display notification …' / BurntToast. Best-effort by design — a freshly joined tunnel may need a few seconds, so a failure is informational, never fatal to enroll. Returns { ok, method }.

    The two gotchas (baked into the scripts, never re-debug)¶

    1. Windows newt MUST run as a SYSTEM scheduled task or the WireGuard adapter is created but never transmits (tunnel one-way). The Windows bootstrap targets an elevated shell; the server-generated script registers the SYSTEM task (RunLevel Highest).
    2. A host-mode mesh resource MUST have a non-empty alias or it never routes (every packet silently dropped). enroll always passes a resource name so the mesh CLI derives <name>.mesh; we never create an empty-alias resource.

    Assumptions: the enrollment token authorizes a GET …/enroll/script the core owner serves (it returns the deviceinstall.js body for that device+OS); deviceinstall.js has no macOS generator yet (the endpoint supplies the launchd plist); the SSH user for the victory lap defaults to ASMLTR_PORTAL_SSH_USER (fallback root); baseUrl resolves from ASMLTR_PORTAL_BASE_URL → ASMLTR_PUBLIC_URL → BASE_URL → the mesh dashboard URL → http://127.0.0.1:3000.

    7. Status — what's actually tested (2026-10-21)¶

    This section is the as-built record: what has run on real hardware vs. what is built-but-unverified vs. designed. Keep it honest as we expand.

    ✅ Proven end-to-end on hardware (Yoga / Windows, asmltr-portal-66DA)¶

    The full bidirectional drive loop works:

    The assistant (server)  →  POST /v2/portal/default/exec   (core relay queue)
              →  phone app background relay polls GET …/exec/next
              →  BLE write to the dongle's `exec` characteristic
              →  dongle: keystroke-script → USB-HID into the focused host window
host output   →  typed cmd writes to the dongle's own CDC serial port
              →  dongle `ioback` NOTIFY  →  phone relay drains it
              →  POST …/io  →  the assistant reads GET …/io

    Verified actions: - OS detection — the dongle fingerprints the host at USB enumeration (Windows via MS-OS-2.0) and shows host: windows on its own screen at plug-in. - HID drive (the assistant → host) — typed text into Notepad; opened an app blind (Win+R → notepad → Enter); drove PowerShell. Keystrokes are reliable after the fix (each press/release held ~30 ms, past the ~10 ms HID poll interval — an earlier 14 ms hold dropped occasional characters). - CDC return (host → the assistant) — wrote to the dongle's serial port from the host and read it back here (ASMLTR-CDC-TEST from <HOST>), and ran a real command whose output returned (whoami=<host>\<user>). This is the feedback loop closing. - On-dongle feedback — the dongle shows each incoming remote command on-screen ("Remote: keys" + snippet, cyan→green LED). - The relay — a poll-relay both ends hit. Three bugs were fixed live to make it work: retry GATT writes on rc 201 (BUSY) + settle after the ioback-subscribe; drop a stale native connection before scanning (a held connection stops the dongle advertising, and the native gatt survives app reloads); hold the link 45 s + keep-alive while ioback streams.

    🔨 Built but not yet live-tested¶

    • Mesh enroll / uninstall / victory-lap (core/src/portal/enroll.js) — joins a host onto the Pangolin mesh, registers ssh/rd, tears down. The install-script endpoint is a flagged placeholder.
    • Vault-kill-switch (dongle-only credential tier, §8b of the asmltr-portal DESIGN).

    📐 Designed, not built¶

    • The hidden session-bridge REPL — the efficiency + non-interference fix. Today every command is HID-typed: slow, and it steals the user's focus/input. The plan is a one-time short HID bootstrap that launches a hidden powershell -WindowStyle Hidden REPL reading the dongle's serial; thereafter commands flow over CDC (fast, reliable, invisible) and screenshots/clipboard come back over CDC. This is the next build.

    Known limitations (today)¶

    • Driving is HID into the user's active session → it steals focus and is visible while typing. Fine when the user is away; the hidden REPL (above) is the fix for background, non-interfering use.
    • Commands are HID-typed one at a time → slow (~30 ms/char) and length-sensitive. The session bridge removes this.
    • The relay keys a single dongle on the channel id default; multi-dongle keys by portal name later.
    • Relay transport is poll-based over core HTTP (not the device-gateway push) — simple and it works.

    Transport: BLE bootstrap + Wi-Fi Direct fast path (R5 — built 2026-10-21, not yet flashed/tested)¶

    The BLE notify return channel can't carry bulk data reliably (a screenshot streamed back dropped mid-transfer; see the firmware reliability notes). Rather than keep fighting BLE throughput, R5 adds a Wi-Fi Direct (Wi-Fi P2P) data transport and keeps BLE as the bootstrap + fallback. This also reflects that Portal management is now native-app-only (the browser-BLE, device-agnostic rationale was dropped) — so the Portal nav item is hidden unless window.AsmltrNative is present.

    Model (mirrors a phone-as-Group-Owner project)¶

    • Phone = Wi-Fi Direct Group Owner (GO); dongle = legacy STA client. The phone keeps its normal Wi-Fi station for internet; the P2P group is a separate interface. No SoftAP (that would steal the phone's internet station). Group is pinned to 2.4 GHz — the ESP32-S3 is 2.4 GHz-only.
    • Creds are not hardcoded (a naive phone-as-GO app hardcodes them): the app generates a per-session passphrase, creates the group, and hands {ssid, pass, ip, port} to the dongle over the BLE WIFI char (0x0A). The dongle joins as STA and opens a TCP client socket to the GO (default 192.168.49.1:9790).

    Smart selection (transparent — one "Adopt", no extra UX)¶

    The relay connects over BLE + pairs as before, then on the first drive tries to upgrade: create group → hand creds over BLE → wait for the dongle's TCP socket. If it lands within ~12 s, exec/ioback route over TCP (transport='wifi'); otherwise it silently stays on BLE. If the socket drops mid-session, it falls back to BLE for subsequent commands. Absent the wifiP2p* native methods (older APK), it's pure BLE — unchanged.

    Wire protocol¶

    • BLE char 0x0A WIFI (WRITE, chunked [flags][rsvd][seqBE] like exec): payload is creds JSON {"ssid","pass","ip","port"}, or {"off":true} to tear Wi-Fi down.
    • TCP framing, both directions: [len:2 big-endian][payload].
    • app→dongle payload = [mode:1][data] (same as the BLE exec char) → engine_submit_exec.
    • dongle→app payload = raw ioback bytes (same as a BLE ioback notification) → one portal.io chunk.
    • The dongle's ioback task is the transport selector: Wi-Fi socket if up, else BLE notify.

    Native bridge (window.AsmltrNative) additions¶

    wifiP2pStart() · wifiP2pInfo() (→ {state,ssid,pass,goIp,port,error}) · wifiP2pSockConnected() · wifiP2pWrite(b64[mode][data]) (native prepends the length frame) · wifiP2pReadIo() (JSON array of base64 ioback frames, mirrors bleNotificationsIo) · wifiP2pStop().

    Firmware build facts¶

    • New wifi_link.{c,h}; BT/Wi-Fi software coexistence on; custom 3 MB app partition (the app outgrew the 1 MB default once Wi-Fi was linked). Binary ~1.22 MB. Wi-Fi is brought up lazily and any failure leaves it inactive → BLE fallback. Flashing a partition-table change needs all three images (0x0 bootloader, 0x8000 partition-table, 0x10000 app).

    ⚠️ Status: built + compiles on both sides; NOT flashed or hardware-tested.¶

    Morning bring-up must verify: Wi-Fi+BLE+USB coexistence boots & stays up (RAM is the top risk — if esp_wifi_init ENOMEMs we stay on BLE, or enable PSRAM); the 2.4 GHz group creation + NEARBY_WIFI_DEVICES runtime prompt on Android; the dongle associates + the TCP socket lands; a large return (the 800-char pattern, then a screenshot) arrives intact over Wi-Fi; and clean BLE fallback when Wi-Fi is refused.

    2026-10-21 — single-owner relay + self-heal (built; partially hardware-confirmed)¶

    The relay is now single-owner: the phone's native foreground service (DeviceControlService) is the SOLE dongle driver, foreground and locked. The webview relay's driving and the foreground/background handoff are gone (that onPause/evaluateJavascript race left the dongle clamped on lock). The service yields the dongle only while the in-app Portal/Adopt screen is open (portalYielded via NativeConfig.portalServiceYield, driven by Portal.vue mount/unmount). Wi-Fi is now negotiated once and held (no per-command re-handshake), and the background ioback pump is continuous while connected. Dongle self-heals a dead link via a ~6s BLE supervision timeout (re-advertises on its own — no replug). Confirmed live: HID drive, Wi-Fi upgrade, CDC round-trip, locked-phone driving, held-Wi-Fi speedup. To confirm: lock-survival with zero replug, and the Portal-screen yield handoff. (APK 0.10.11.)

    Connection & drive — FINAL confirmed state (2026-10-21)¶

    Supersedes the "built / not-yet-tested" caveats in the R5 and single-owner sections above — the whole loop is now hardware-confirmed (Yoga / Windows, asmltr-portal-66DA; app ≥ 0.10.14).

    Connection model (what actually happens)¶

    • Single owner: the phone's native DeviceControlService is the SOLE dongle driver — foreground AND locked. No webview relay, no fg/bg handoff. It yields the dongle ONLY while the in-app Portal/Adopt screen is open (NativeConfig.portalServiceYield ← Portal.vue mount/unmount).
    • Always-on auto-connect: whenever a paired dongle advertises (and not yielded), the service scans + connects + holds — proactively, no command needed. The old idle-disconnect is gone (always-held; reliability over battery, by explicit choice).
    • Wi-Fi on connect + held: portalTryWifiUpgrade runs immediately on connect and holds the P2P socket; opportunistic 30s retry if still on BLE (err:perm handled, hint posted once).
    • Self-heal: portalHealthCheck every ~15s does an INFO-read keepalive; a dead/wedged GATT (read can't issue / gattResult error|disconnected / stuck in reading >6s) → drop → rescan → reconnect. A failed drive also drops+reconnects. Dongle side: ~6s BLE supervision timeout → it re-advertises itself. Net: no force-stop, no replug to recover.
    • Screen-off discovery: the dongle advertises its service UUID in the PRIMARY adv packet, and the app scans filtered by that UUID — the only kind of scan Android runs with the screen off. This is what makes cold, locked discovery work.
    • Reliable bulk return: the relay batches all ioback chunks drained per ~300ms tick into one POST (was one POST per ~512 B chunk → ~70 round-trips → slow + truncated) and retries a failed POST 4×. A full-res screenshot now returns whole over Wi-Fi.

    Dongle UX (firmware)¶

    • Corner status light: 🔴 no phone · 🔵 BLE · 🟢 Wi-Fi. Back LED: magenta = sending to host, cyan = receiving from host (HID / CDC / install — any mode).
    • Screen: full-screen holding page only when disconnected; install/remove/status menu when connected; CDC/remote panels redraw in place with a 2.5s activity-debounce (no strobing / flicker).

    Operating the drive loop¶

    • Default to HEADLESS. Once the session bridge is up, do work as CDC commands in the invisible PowerShell (file queries, installs, config, screenshots) — nothing pops up or steals the user's focus. Use visible HID typing / opening a GUI app ONLY when the task needs the screen or the user asks for an on-screen action (say so first if you must open a window). HID is the bootstrap + fallback, not the default way to do work.
    • Couple the screenshot to the action — put navigate + render-wait + capture + write-back in ONE CDC command, so you act and observe in a single round-trip (the autonomous do→see→decide loop).
    • BLE for text, Wi-Fi for bulk. A big return (screenshot/file) over BLE still drops its tail.
    • REPL bootstrap is fragile across reboots (dongle reflash / app update kills it). Re-bootstrap: kill any stale shell holding the dongle's COM first (it blocks a fresh launcher), then launcher→RDY→body.

    ⚠️ Gotchas that aren't bugs¶

    • Wi-Fi Direct ✗ while hotspot/tethering is ON — the Wi-Fi chip is out of interfaces (STA+AP), so group creation fails and it stays on BLE (🔵 not 🟢). Turn the hotspot off → auto-upgrades to 🟢. (logcat tell: Failed to create P2p iface … Interface resource is not available.) TODO: surface this to the user instead of a silent blue-not-green.
    • BT headset call starves BLE discovery (shared radio) — a cold connect may fail until the call ends.
    • Android wireless-debug port rotates — if using adb to introspect the phone, re-read the port.
